# Sandbox-concurrency ablation (Demo 1): finding the goodput sweet-spot

## The question

Demo 1 (the **A-series**: [`demo_cpu_single`](../code/demos/demo_cpu_single/) in-process mini harness, and its
two-Runtime sibling [`demo_cpu_2runtime`](../code/demos/demo_cpu_2runtime/)) splits the box **4 GPUs trainer + 4 GPUs
inference**. Rollouts are generated by the **harness + inference engines + sandboxes** and dropped
into a **replay buffer**; the trainer **continuously** samples that buffer to take GRPO steps. The
one free knob we vary here is **how many sandboxes / agentic episodes run concurrently** (`C`).

> **Claim under test:** goodput is a **non-monotonic (inverted-U)** function of sandbox concurrency
> `C`. Too few starves the trainer and inference engines; too many floods the buffer with **stale,
> off-policy, clipped** samples that cost compute but contribute little (or biased) gradient. There
> is a **sweet spot**, and Demo 1 is the right, cheap vehicle to find it.

This doc defines the trade-off, the metrics, how each is read from *our* logs, the sweep protocol,
and the decision rule for picking `C*`.

---

## Why there is a trade-off (the mental model)

An agentic rollout is **not** GPU-bound end to end. One episode alternates between two very
different phases:

```
 episode timeline (one of C concurrent):
   [decode turn] --wait--> [sandbox: write_file/exec/run_checks.py] --wait--> [decode turn] ...
   ^ uses inference GPU          ^ inference GPU IDLE for THIS episode         ^ ...
```

The **decode** phase uses an inference GPU; the **sandbox** phase (tool exec, the MBPP
`run_checks.py`, plus — in `demo_cpu_2runtime` — two `invoke_agent_runtime` round-trips to remote Runtimes)
leaves that episode's share of the inference GPU idle. So the whole disaggregated system is a
**pipeline with a slow, bursty, IO-bound stage** (the sandbox) feeding a fast, expensive stage (the
trainer), buffered in between.

### Low-`C` failure: starvation (a Little's-law problem)
With too few concurrent episodes, whenever the in-flight episodes are all blocked on their sandboxes
the inference engines have **nothing to decode** — batch occupancy collapses (`#running-req → 0`),
token throughput drops, the buffer drains, and the **trainer stalls waiting for data**. To keep the
inference engines saturated you need roughly

```
C  ≳  (mean episode wall-time / mean per-episode decode-time) × (inference concurrency)
```

concurrent episodes to **hide the sandbox latency** — classic latency hiding. In `demo_cpu_2runtime` the
sandbox phase is a *remote* CPU Runtime invoke, so its latency is large and `C` must be
correspondingly larger before the engines stay busy.

### High-`C` failure: staleness & off-policy-ness — *only in fully-async mode*
As `C` grows, generation outruns training, so samples sit longer in the buffer and are consumed at a
later policy version than they were generated at: **`staleness = v_use − v_gen` grows**. Staleness
means the **behavior policy** that generated the tokens diverges from the **target policy** being
optimized, so the importance-sampling ratio `ρ = π_target/π_behavior` drifts from 1. Then, in order:

1. **raw IS ratio** spreads away from 1 (variance ↑),
2. more tokens hit the **PPO clip** boundary → **`pg_clipfrac` ↑** (clipped-rollout ratio ↑),
3. the off-policy IS correction (TIS) clamps more weights → **`tis_clipfrac` ↑**,
4. filters/staleness caps **discard** more samples → **discard ratio ↑**.

The gradient from a heavily-clipped, stale batch is **biased and dampened** — you burned inference +
sandbox compute to generate tokens that barely move the policy. **Raw throughput keeps rising with
`C`; goodput does not.** **But this failure only appears if the buffer is allowed to grow deep — see
the next section, because Demo 1's default driver does *not* let that happen.**

## Two async modes — this decides which trade-off you're actually measuring

The word "async" hides two very different regimes, and **which one you run changes the entire
shape of the ablation.** slime ships both.

### Mode A — 1-step-async (`train_async.py`) — Demo 1's *default*, **staleness-bounded**
`train_async.py` is a **one-step-ahead pipeline**, not a deep buffer:

```python
next_future = generate.remote(0)                 # kick off rollout 0
for rollout_id in ...:
    curr = get(next_future)                       # wait for rollout N
    next_future = generate.remote(rollout_id + 1) # start N+1 ── overlaps train(N) ──┐
    train(curr)                                   # train on rollout N ───────────────┘
```

There is **only ever one outstanding `generate` future**; `generate(N+2)` cannot start until
iteration `N+1`. The rollout buffer (`RolloutDataSourceWithBuffer.buffer`, a FIFO Python list, **no
capacity arg**) therefore holds only **≈ one rollout** = `RB` groups = `RB × NS` samples (Demo 1:
`4 × 8 = 32`), plus any dynamic-sampling oversample surplus. Consequences:

- **Staleness is capped at ≈ 1 rollout step** (or `update_weights_interval`) **regardless of `C`.**
- So the high-`C` failure is **NOT** the staleness/clip/discard blow-up above. Those metrics stay
  roughly flat. The high-`C` failure here is **diminishing returns / wasted cost**: once
  `generate(N+1)` finishes faster than `train(N)`, the extra sandboxes and inference sit **idle**
  waiting for the lockstep.
- **What the ablation measures in Mode A:** a pure **overlap** problem. Sweet spot = the *smallest*
  `C` that makes `generate-time ≤ train-time` so the two fully overlap (`wait_time_ratio → 0`, MFU
  maxed). Track **goodput + `wait_time_ratio`**; `pg_clipfrac`/IS/staleness are ~constant controls
  that confirm you're *not* off-policy. **Use Mode A to answer "how many sandboxes to stop starving
  the trainer, at minimum cost."**

### Mode B — fully-async (rollout-buffer plugin) — **staleness-dominated**
The `slime_plugins/rollout_buffer` plugin runs a **separate FastAPI buffer server** (`buffer.py`)
that continuously generates trajectories (via a `Generator.run_rollout()` hitting slime's LLM
server) and holds them in a `BufferQueue`; the trainer pulls batches over HTTP
(`--rollout-function-path …generate_rollout --rollout-buffer-url …`). Generation and training are
**fully decoupled** — generation is *not* lockstepped to one rollout ahead, so:

- the buffer **grows deep**, samples age, and **staleness genuinely rises with `C`**;
- the `BufferQueue` timestamps each group and can **discard** ones that exceed a staleness/timeout
  bound (a real, tunable **discard ratio**);
- so the whole staleness → raw-IS-drift → `pg_clipfrac`↑ → `tis_clipfrac`↑ → discard↑ chain above
  **is now live**, and goodput becomes a true inverted-U.
- **What the ablation measures in Mode B:** the real **goodput sweet-spot under off-policy pressure**
  — the classic staleness-vs-throughput trade-off. **Use Mode B to answer "how deep can we push
  sandbox concurrency before stale/clipped/discarded rollouts eat the gains."**

> **Bottom line:** to study the *staleness/discard/clip* trade-off you asked about, you must run
> **Mode B**. In Mode A those metrics are pinned flat by the 1-step lead, and the only thing you can
> tune is overlap. This doc's sweep protocol below is written for **Mode B** (the deep-buffer study);
> the same `C` / `INFER_CONC` knobs apply, but the interpretation of the high-`C` end is the
> inverted-U, not just diminishing returns.

### The picture
```
   goodput ▲
           │            ___ sweet spot C*
           │        _.-'   `-._
           │     .-'           `-.__
           │  .-'                    `----____   (staleness / clip / discard dominate)
           │.'
           └───────────────────────────────────▶  sandbox concurrency C
             starved      balanced        flooded
   MFU:       low   →     high (plateau)  →  high but wasted on stale data
   staleness: low  →      moderate        →  high
   clipfrac:  low  →      moderate        →  high
```

## The metrics — definitions and how we read them *in this repo*

Most of these are already emitted by slime into the train log and/or derivable from it. `metrics.py`
in each demo parses them (`rollout/raw_reward`, `perf/step_time`, `perf/wait_time_ratio`,
`train/pg_loss`, `train/kl_loss`, `train/train_rollout_logprob_abs_diff`) plus the two latencies we
instrument ourselves (last two rows below): the **sandbox response time** and the **pure SGLang
decode time**, split out of slime's aggregate `perf/rollout_time` (which otherwise lumps decode +
sandbox round-trips + harness overhead together). This split is what actually answers "is the
sandbox the bottleneck?" — the headline question of this ablation.

| Metric | Definition | Source in our stack |
|---|---|---|
| **Goodput** | *Useful* work/sec = (rollout tokens that actually land in a gradient step) / wall-clock. The optimization target — throughput net of discard & clip. | Derived: `perf/actor_train_tok_per_s × (1 − discard_ratio)`, cross-checked against samples/sec that pass the buffer filter. |
| **MFU** | Model-FLOPs utilization = achieved trainer FLOPs / peak. High ⇒ trainer GPUs fed & busy. | Derived from `perf/actor_train_tok_per_s` + Qwen3-4B FLOPs/token; **starvation proxy** = `perf/wait_time_ratio` (fraction of step time the trainer *waits* for data). `MFU_effective ∝ (1 − wait_time_ratio)`. |
| **Staleness** | `v_use − v_gen` (policy-version lag when a sample is consumed). | Weight version bumps in `update_weight_from_distributed.py` (`self.weight_version += 1`); **direct proxy** = `train/train_rollout_logprob_abs_diff` = `‖logπ_target − logπ_behavior‖` on the same tokens. Bigger ⇒ staler. |
| **Discard ratio** | Fraction of generated rollouts never used for a gradient (staleness cap, buffer overflow, GRPO all-equal-reward groups with zero advantage variance, truncated/malformed trajectories). | Buffer/oversample path (`RolloutDataSourceWithBuffer`, `--mask-offpolicy-in-partial-rollout`, buffer-filter) — count generated vs consumed per rollout id. |
| **Raw IS ratio** | `ρ = exp(logπ_target − logπ_behavior)`, unclipped importance weight. Near 1 ⇒ on-policy. | `importance_ratio = torch.exp(log_probs − old_log_probs)` (loss.py); TIS/OIS weights `tis`, `ois = exp(−ppo_kl)`. Log mean & p95. |
| **Clipped IS ratio** | `ρ` clamped to the IS bounds `[tis_clip_low, tis_clip]` (off-policy TIS correction). | `tis_weights = clamp(tis, tis_clip_low, tis_clip)` (loss.py). |
| **Ratio of clipped rollouts** | Fraction of tokens/samples that hit a clip boundary — the headline "how off-policy is my batch" number. | **`pg_clipfrac`** (PPO clip, `compute_policy_loss`, our `eps_clip=0.2 / eps_clip_high=0.28`) and **`tis_clipfrac`** (IS clip). |
| **Sandbox response time** | Wall-clock of each `invoke_agent_runtime` round-trip (write_file / exec / read_file / ping), retries included — the real per-op latency the rollout paid. Rises with `S` iff the sandbox fleet is the bottleneck. | **We instrument it**: `agentcore_runtime_sandbox._timed_invoke` prints one `[sbx-op] op=… ms=…` record per op; `metrics.py` writes a raw `*.sandbox_ops.csv` + per-step `perf/sandbox_ms_{mean,p50,p95}` (and `perf/sandbox_count`) columns, and a run-level per-op summary. |
| **SGLang decode time** | Wall-clock of the pure `/generate` POST only (no tokenization / sandbox / harness). Isolates inference latency so it can be compared against sandbox time inside one rollout. | **We instrument it**: `policy.SGLangPolicy.complete` prints one `[sglang-gen] ms=…` record per decode; `metrics.py` writes a raw `*.sglang_gen.csv` + per-step `perf/sglang_gen_ms_{mean,p50,p95}` columns. |

Reward sanity (`rollout/raw_reward`) must stay nonzero throughout — a stale/broken run that trains
on garbage can look "fast" while learning nothing, so goodput is only meaningful alongside a healthy
reward curve.

## Experimental design

**Independent variable:** episode/sandbox concurrency `S`. In the runner this is realized by
`CONC` (`--sglang-server-concurrency`, per engine × 2 engines): `S = CONC × 2`. Sweep e.g.
**`S ∈ {2, 4, 8, 16, 32, 64}`** (`CONC ∈ {1,2,4,8,16,32}`; `demo_cpu_single` today runs `CONC=4` ⇒ `S=8`).

**Decoupling inference concurrency `I` from sandbox count `S` (`INFER_CONC`).** By default slime's
one semaphore ties both together, so raising `S` also raises how many episodes decode at once. To
hold inference load **fixed** while varying `S` alone, set `INFER_CONC=I` (e.g. `8`): a
process-global semaphore in `SGLangPolicy.complete` wraps only the SGLang decode POST, so at most
`I` episodes decode concurrently no matter how large `S` is (the extra `S − I` are in sandbox ops or
waiting). Then sweep `CONC` (→ `S`) with `INFER_CONC` pinned. Constraints/notes: keep `I ≤ S` or the
gate never binds (at `CONC=4, INFER_CONC=8` you get `S = I = 8`, the coupled baseline); and the gate
is per rollout **process** — it assumes slime drives all `generate()` coroutines from one event loop
(it does), so verify if you ever shard rollout across workers. `INFER_CONC=0`/unset = disabled
(original coupled behavior; other demos unaffected).

**Held fixed (controls):** 4 trainer + 4 inference GPUs, TP=2/PP=2, Qwen3-4B, the dataset and
`RB`/`NS`, the async decoupled setup, the staleness/buffer policy, and — importantly — the
**router policy** (use `round_robin`, the recommended default for the sweep, so both engines actually serve;
otherwise `cache_aware` pins all shared-prefix traffic to one engine and confounds the inference
half of the study). Run enough steps per point that the metrics reach steady state (the first step
or two are warm-up; the smoke `NR=11` is fine for a quick pass, longer for publishable curves).

**Two vehicles, on purpose:**
- **`demo_cpu_single` (mini harness, in-process, local/CPU sandbox)** — cheapest, cleanest isolation of the
  knob; fast iteration.
- **`demo_cpu_2runtime` (mini harness on its own Runtime + remote CPU sandbox Runtime #2)** — has the
  **realistic sandbox latency** (remote `invoke_agent_runtime` per tool call), which is exactly what
  makes the low-`C` starvation regime real. This is where `C*` actually matters operationally.

**Per point, record:** `goodput`, `MFU`/`wait_time_ratio`, `staleness` (logprob-diff + version lag),
`discard_ratio`, `mean|p95 raw IS`, `mean clipped IS`, `pg_clipfrac`, `tis_clipfrac`, and
`rollout/raw_reward` (health). Plot each vs `C`.

**Decision rule for `C*`:** pick the **knee of the goodput curve** — the largest `C` before
`wait_time_ratio` bottoms out *and* before `staleness / pg_clipfrac / discard_ratio` begin their
steep rise. Concretely: increase `C` while `d(goodput)/dC > 0` and `pg_clipfrac`, `discard_ratio`
stay under a chosen budget (e.g. clipfrac < ~0.2, discard < ~10%); stop at the first `C` that
violates the budget or flattens goodput.

## What I think (my read on the trade-off)

- **The knob that matters is the sandbox stage's latency-to-decode ratio, not `C` in the abstract.**
  For `demo_cpu_single` (local, fast sandbox) the pipeline is nearly compute-bound, so a *small* `C` already
  saturates the engines and the goodput curve peaks early then decays fast into staleness. For
  `demo_cpu_2runtime` (remote CPU sandbox — big, variable invoke latency) you need a *larger* `C` just to stop
  starving, so its peak sits further right. **`C*` is demo-specific;** I'd expect `demo_cpu_single`'s optimum
  around the low single digits and `demo_cpu_2runtime`'s meaningfully higher.

- **Watch `wait_time_ratio` and `pg_clipfrac` as the two guardrails.** They fail in opposite
  directions: `wait_time_ratio` high ⇒ under-provisioned `C` (trainer starving, MFU wasted);
  `pg_clipfrac`/staleness high ⇒ over-provisioned `C` (buffer flooded, gradient dampened). The sweet
  spot is where **both are simultaneously acceptable** — that window is `C*`. Goodput is the scalar
  that summarizes it, but those two diagnostics tell you *which side* you're on when you're off it.

- **Our current `demo_cpu_2runtime` `CONC=4` (⇒ 8 concurrent) is a guess, not a measured optimum** — this
  ablation is exactly how we replace the guess. My prior: with the remote CPU sandbox latency, 8 may
  be *slightly under* the starvation threshold (the round-robin run showed only ~4-5 `#running-req`
  per engine, i.e. the engines are not always full), so `C*` is plausibly a bit higher — but only up
  to where staleness/clip start climbing. The ablation will show the exact crossover.

- **Off-policy correction (TIS) moves the sweet spot right, at a cost.** Enabling TIS
  (`compute_policy_loss` + IS clamp) lets the trainer tolerate more staleness before the gradient
  degrades, so it *widens* the usable `C` band — but `tis_clipfrac` then becomes the thing to watch
  (heavily-clamped IS weights are corrected-but-high-variance). Worth running the sweep both with and
  without TIS to see how much headroom it buys.

- **Goodput ≫ raw throughput as the target.** It's easy to "win" by cranking `C` and reporting more
  tokens/sec; that's a trap if half of them are discarded or clipped to near-zero effect. The whole
  point of this study is to optimize the *useful* number, which is why every throughput point is
  paired with staleness/clip/discard.

**Bottom line:** yes, the purpose is to locate the concurrency `C*` that maximizes **goodput** —
enough sandboxes to hide sandbox latency and keep the 4 inference + 4 trainer GPUs busy (high MFU,
low `wait_time_ratio`), but not so many that the buffer fills with stale, heavily-clipped, discarded
rollouts. Demo 1 is the right, cheap harness for it, and every metric you listed is already in our
logs — so this is a measurement exercise, not a re-instrumentation one.
